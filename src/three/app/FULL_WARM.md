# Full warm: загрузка High

В production полный прогрев обязателен. Для проверки того же пути в Vite dev:
`/?tier=high&fullWarm=1`. Без `fullWarm=1` сохранён быстрый development-старт.
`fullWarm=0` не отключает production gate.

До Start обычный update/render loop уступает renderer подготовке. Clock продолжает
сбрасывать delta, HTML-прелоадер продолжает анимироваться. Ошибка подготовки или
потеря контекста не открывает Start.

`PreparationScheduler` собирает небольшие CPU-задачи в бюджет 3 мс. Каждый GPU
проход получает отдельный rAF, после задачи длиннее 8 мс добавляется свободный кадр.
Это кооперативный бюджет: отдельный вызов WebGL-драйвера нельзя прервать через JS.
Three r155 получает материалы небольшими порциями с исходными lighting/fog/instancing
параметрами. Точечный backport асинхронной компиляции описан ниже: версия Three,
исходники шейдеров High и настройки качества сохранены.

Сохраняются реальные draw всех сцен и всех направленных ring-пар, case↔home/hub
при наличии кейсов; deep-link active→home идёт последним. При переборе соседних
пар с одинаковым source переиспользуется композиция A. Дополнительные полноэкранные
RT не создаются. Screen HUD, fog-вариант home-label и временно отсоединённые
логотипы Contacts тоже компилируются и рисуются под прелоадером.

Из загрузки исключены HUD отсутствующих case-сцен и demo-route вне его прямого
адреса. Постеры опубликованных проектов загружаются параллельно, загружаются в GPU
по одному; при ошибке/отмене освобождаются и поздние результаты запросов.

High использует `public/models/home/whale-high.glb`: исходные вершины/рёбра/скелет,
один реально используемый SWIM clip. Невидимые материалы источника частиц заменены
одним базовым материалом, чтобы glTF не дробил геометрию на material primitives.
Medium/low сохраняют исходный FBX и hologram path. Обновление/проверка модели:

```sh
node tools/assets/prepareWhaleHigh.mjs
node tools/assets/prepareWhaleHigh.mjs --verify
node --test src/three/app/preparationScheduler.test.js src/three/renderer/compileSceneChunked.test.js
```

Проверка модели сравнивает порядок вершин, topology и положения всех вершин в
девяти точках SWIM. Допуск в мировых единицах исходного FBX — 0.001; получено
0.00007361. Из 18 FBX-анимаций в High используется только SWIM. Размер 2 944 972 →
2 181 016 байт. Количество частиц на High осталось 60 822.

Контроль 10.09.2026: production preview, High, 1440×900 CSS, DPR 2, RTX 3070 Ti,
прогретый shader/browser cache. `_prepareApplication`: 17.19 → 8.91 с; 56 hex-пар
сохранены, scene warm draws: 123 → 75. Длинные задачи до ready: 17 → 7,
максимальная: 305 → 98 мс. Это замер на одной машине, не гарантия времени на
холодном драйвере или медленной сети. Бюджет кадра и runtime CPU-эффекты остаются
отдельной работой; результат следующего этапа для кита приведён ниже. Нулевые
просадки на любом устройстве не заявляются.

После прогрева 122 GPU-программы; Start, первые входы и возвраты через home,
portfolio, about, contacts и все четыре capabilities сохраняют это число.
В проверенных переходах/скролле не было Long Tasks (>50 мс). Полный редизайн
medium/low/mobile и изменения визуальных эффектов в эту ветку не входят.

## High: GPU-анимация кита (пункт 4)

`whaleParticleSkinning.js` готовит исходные концы рёбер, индексы/веса костей и
маленькую текстуру матриц. `whaleParticleSkinning.glsl.js` деформирует каждый конец
отдельно, затем интерполирует частицу между ними. Интерполировать исходные веса
вместо уже деформированных концов нельзя: это меняет форму рёбер.

Все 60 822 частицы, SWIM, локальные трансформации, breathing, свечение и маска
плавника сохранены. Маска яркости теперь вычисляется в vertex shader. Атрибуты
частиц после подготовки не меняются; за кадр передаётся 2 400 байт матриц вместо
973 152 байт позиций/яркостей. Дополнительные статические GPU-атрибуты занимают
около 4,9 MiB и загружаются при реальном draw под прелоадером. Дополнительного
render pass нет. Материал освобождает текстуру матриц при dispose, включая
пересборку плотности в dev-панели и отменённую загрузку сцены.

Шлейф читает только нужные ему живые точки через `bodySamples.getPosition`.
Для его длины/спавна сохраняется точный min/max X всех исходных концов рёбер:
это короткий проход по заранее подготовленным коэффициентам, без полного
CPU skinning облака и без чтения GPU обратно на CPU. Обычный уход со страницы
не уничтожает эти данные. Medium/low используют прежний hologram path.

Проверка 10.09.2026 на той же машине, 1440×900 CSS / 2880×1800 framebuffer:

- Старый `updatePositions`: среднее 6,14 мс, p95 7,9 мс (dev, полный прогрев).
- Новый `updatePositions`: около 0,02 мс; весь шлейф вместе с точными границами
  около 0,6 мс (production). Остальные эффекты страницы в эти числа не включены.
- Изолированный draw кита, GPU timer query, 12 замеров каждого варианта:
  0,28 мс с загрузкой CPU-позиций → 0,24 мс с GPU skinning. Это время одного
  draw, а не всего сайта; цифры зависят от GPU.
- Реальный float-RT readback: 547 398 проверенных положений (9 поз × 60 822),
  максимальное отклонение от CPU-проверки палитры 0,000266 единицы модели.
  Node-тест отдельно сравнивает палитру с исходным `applyBoneTransform` по всей
  геометрии, включая цикл SWIM, трансформации родителя и ненормированные веса.
- Полная подготовка приложения: 9,11 с против предыдущего замера 8,91 с;
  гейт Start по-прежнему ждёт реального прогрева. При первом обходе home → portfolio
  → about → contacts и обратно сохранялись 122 программы и тот же объект кита;
  версии атрибутов не менялись. Resize и отмена скролла не пересоздают облако.
- Touch-навигация home → portfolio → home не дала Long Tasks. Потеря контекста
  останавливает rAF; удаление приложения освобождает палитру один раз.
  Проверены lint и build.

```sh
node --test src/three/scenes/home/utils/whaleParticleSkinning.test.js
```

В общем обходе страниц с resize ещё наблюдались отдельные задачи 61–75 мс.
Этот этап убирает CPU skinning кита, но не означает устранения всех задержек
остальных сцен, DOM/Canvas-эффектов или изменения разрешения (пункты 5–6).

## High: подготовленные Home-тексты (пункт 5)

`heroText/gpu` обслуживает tagline, tech-stack и «Листайте вниз» только на High.
Основной DIGITAL MONSTER остаётся на прежнем instanced path. Medium/low сохраняют
`HeroTextMesh` / `HeroScrollHintMesh` и их текущий рисунок.

- Все три локали и используемые ими замены букв готовятся после загрузки шрифтов
  до Start. Маленькие glyph-ячейки и общие symbol-ячейки упакованы в три атласа;
  порядок, метрики и UV хранятся в статических instanced attributes. Нет кадровых
  полноэкранных снимков текста. Canvas painting уступает кадр после 3 мс работы.
- Размер при DPR 2: 2048×178 (hint), 2048×666 (tagline), 2048×216 (stack),
  суммарно 8 683 520 байт RGBA8, около 8,28 MiB GPU storage без mipmaps.
  Исходные Canvas-буферы также остаются в памяти. Обычные смены языка не создают
  дополнительные атласы; изменение viewport меняет размещение через uniforms.
- Сохранены исходные тексты, шрифты, интервалы, группы волн, замены символов,
  тайминги и звук. Один конечный playhead каждого блока выбирает подготовленные
  буквы на GPU. Мышь, колесо и бегущий хвост рисуются аналитическим шейдером.
  Неподвижный блок не запускает отдельные таймеры/rAF и не обходит буквы на CPU.
- Чистые буквы выводятся после bloom с привязкой к пикселям renderer; HDR-символы,
  декоративная линия и мышь используют существующий bloom. При hex те же ресурсы
  входят в models-слой, screen-дубль отключается. Dormant не уничтожает ресурсы,
  скрытая подсказка не продолжает свой playhead. Отмена подготовки и dispose
  освобождают ресурсы, позднее завершение шрифтов не создаёт новый atlas.

Проверка 10.09.2026: production preview, High, Chrome, 1440×900 CSS / DPR 2,
RTX 3070 Ti. Это локальные контрольные замеры, не гарантия для любой машины.

- До изменения за 2 с покоя подсказка перерисовывалась 121 раз; при RU→EN
  tagline и stack добавляли по 62–63 перерисовки. После изменения — 0 вызовов
  `fillText`, `clearRect`, `measureText` на трёх атласах за весь проверочный обход.
  Версии текстур остались 1, UUID текстур и геометрии не изменились.
- Обновление всех трёх GPU-блоков за 2 с заняло суммарно около 2,2 мс CPU;
  старый Canvas draw одной подсказки — около 25,9 мс за тот же интервал.
  Это стоимость этих элементов, а не время полного кадра.
- Последовательный A/B в одном браузере, прогретый shader cache: подготовка
  старого варианта 8,63 с, нового 8,80 с. При первом применении новых шейдеров

- **Холодный драйвер остаётся отдельной проблемой:** старый вариант в том же

- После прогрева — 123 программы; RU/EN/ZH, быстрые повторные переключения,
  home → portfolio → about → contacts → home, малые/большие wheel-дельты и

## Synthetic Core: сокращение холодной компиляции HUD

В `syntheticCoreHudMaterials.js` вложенные смешивания `assemblyLabel` заменены
взвешенной суммой шести состояний с единственным местом вызова `snakeLabel`
в цикле. Формула, строгие пороги покоя, атласы, цвета, рисунок змейки, альфа
и существующие uniforms сохранены. Новый CPU-цикл, draw pass или текстура
не добавлены. Подробности формулы — в `src/three/GPU_GLITCH_SNAKE.md`.

Контроль 10.09.2026, Chrome / RTX 3070 Ti, отдельные свежие browser sessions:

- Полный cold-start A/B текущего сайта с заменой только исходника этого шейдера:
  `_prepareApplication` 16,32 → 13,64 с. RT/screen-компиляции `core-action-hud`
  1452/1389 → 85/87 мс. Количество программ после прогрева одинаковое: 122.
- Изолированная проверка с реальными атласами, 231 состояние (включая RU/EN/ZH,
  скрытую/завершённую змейку и края порогов): все 221 760 000 RGBA8-компонент
  совпали. Отдельный GPU timer query даёт ~0,021 → ~0,019 мс на смешанный HUD,
  то есть главный выигрыш относится к компиляции, а не постоянному FPS.
- В реальной сцене проверены hover с быстрым уходом/возвратом, импульс,
  раскрытие сферы, локали, resize, touch, hex-уход и возврат через history.
  Нет Canvas paint, версии трёх текстур остаются 1, UUID mesh/material/geometry
  не меняются, Long Tasks в этом окне взаимодействия отсутствовали. Hex переносит
  панель в models, возврат восстанавливает screen-overlay.
- Потеря контекста останавливает rAF и запускает штатный fallback; dispose
  освобождает три текстуры. Целевой lint и production build прошли.

В холодном прогреве остаются другие длинные задачи, максимальная в этом A/B —
около 0,8 с. Эта правка устраняет две прежние блокировки по ~1,4 с именно у HUD
сферы; весь проект пока нельзя считать свободным от загрузочных фризов.

## City: первый снимок отражений без общей синхронной компиляции

Следующий профиль связал паузу 0,8 с с `prepareCityOfficeReflections`: первый
`renderer.render()` грани куба создавал сразу несколько архитектурных программ.
Теперь перед шестью снимками `compileSceneChunked` готовит их с бюджетом
`PreparationScheduler`, уступая кадры между дорогими материалами. Первый шаг
тоже начинается после уступки кадра, отдельно от сборки capture-сцены.

Для этого capture использует `visibleOnly`: скрытые офисные поверхности и
ветки не компилируются. Обычный прогрев сохраняет прежнее поведение и готовит
также dormant/hidden-объекты. Helper восстанавливает RT, активную cube face и
mip после каждого задания, включая ошибку. Отмена освобождает временный куб,
небо и возвращает видимость материалов; снимки после отмены не выполняются.

Контроль 10.09.2026, production High, Chrome, 1440×900 CSS / DPR 2, RTX 3070 Ti:

- A/B в двух свежих browser sessions одной сборки, с отключением только нового
  вызова компиляции для baseline: первый cube draw 746,6 → 6,4 мс. Компиляции
  распределены между кадрами, максимальная для probe — 158,6 мс. Это разделение
  работы, а не устранение стоимости каждого отдельного шейдера.
- Полная подготовка 14,40 → 13,90 с, число программ одинаковое: 126. В финальной
  проверке deep link города после добавления начальной уступки кадра: 14,06 с,
  первый draw 5,3 мс, максимальная probe-компиляция 151,7 мс. Время зависит от
  оборудования/кеша; вывод этого шага — плавность улучшена без удлинения до минуты.
- DPR 2, куб 256×256 на грань, материалы, свет и постобработка сохранены.
  SHA-256 исходных HalfFloat-буферов всех шести граней совпали в baseline,
  A/B и финальном deep-link запуске: 1 572 864 RGBA-компоненты без изменений.
- После Start: city → home → history back/city → portfolio → about → contacts
  → about → portfolio → home, wheel с разворотом и resize до 1280×800.
  В этом окне Long Tasks отсутствовали; куб не рисовался повторно, UUID/версия
  отражений сохранились, число программ не выросло. Потеря контекста остановила
  rAF и включила штатный fallback.
- Целевые lint, 9 тестов scheduler/compile/cancel и production build прошли.

Вне этой группы в финальном cold start остаются отдельные компиляции до ~316 мс
и ранняя загрузка/инициализация ~428 мс, ещё требующая отдельной атрибуции.
Нулевые фризы всей загрузки этим шагом не заявляются. DPR не снижен.

## About: сокращение холодной компиляции плазменного стекла

Профиль связал следующую паузу ~325 мс с `aboutFrontGlassMaterial.js`:
программа впервые создавалась на объекте `Back`. Это один ShaderMaterial,
а не серия draw или создание текстур. Ожидание компилятора происходило внутри
`getProgramInfoLog`; отключение диагностики лишь переносило бы ожидание.

Пять мест вызова пятиоктавной `fbm` заменены одним вызовом в цикле по пяти
полям. Сначала вычисляются оба компонента warp, затем зависящие от них поля
филаментов и независимое поле обода. Координаты, порядок арифметики внутри FBM,
все пять октав, dissolve, цвета, прозрачность и временные коэффициенты сохранены.
Это не кеш между кадрами: поля по-прежнему вычисляются для текущего пикселя/времени.
Число проходов и ресурсов, DPR и настройки High не менялись.

Контроль 10.09.2026, Chrome / RTX 3070 Ti, production High, 1440×900 CSS / DPR 2:

- Свежие browser sessions одной сборки, baseline заменяет только фрагмент расчёта
  стекла: компиляция `Back` 328,9 → 157,6 мс. Максимальный job основного scheduler
  329 → 227,4 мс. Количество программ после warm — 126 в обоих вариантах.
- `_prepareApplication` 14,25 → 14,18 с: общий старт остался около 14,2 с,
  главный результат — сокращение одной блокировки, а не ускорение всей загрузки
  вдвое. Остальные программы ещё требуют работы.
- Изолированный реальный GPU: 3 ракурса × 4 времени × 6 dissolve-режимов ×
  7 значений dissolve = 504 состояния, RT 600×400 RGBA8. Все 483 840 000
  компонентов совпали, максимальная разница — 0. Финальный production shader
  совпадает с проверенным после удаления комментариев/пробелов.
- В отдельном GPU timer-тесте при RT 1440×900, 30 чередующихся измерений на
  вариант, без disjoint/GL errors: mean 0,512 → 0,544 мс, median 0,373 →
  0,388 мс. Небольшая цена дополнительного управления циклом учтена; эта правка
  направлена на cold compile и не заявляется как ускорение постоянного GPU draw.
- В живом About проверены wheel, быстрый разворот, touch с возвратом, resize,
  portfolio ↔ about ↔ contacts и home. Частичный обратный ring hex достигал
  ~0,56 и отменялся с возвратом в About (hex=0). В проверенном окне Long Tasks
  отсутствовали, UUID/версии материалов и текстур сохранялись, программы не росли.
  Потеря контекста остановила rAF; обе стеклянные material освобождены по одному разу.
- Целевой lint, production build и GPU-сравнение прошли.

Ранний пик также атрибутирован: сам `canvas.getContext("webgl2")` занял
231–315 мс из стартовой задачи 368–441 мс. Это синхронное создание контекста
браузером, его нельзя разделить scheduler-ом JS. Остальную работу конструктора
можно исследовать отдельно. Следующая дорогая компиляция в warm — около 230 мс.

## Общий bloom/output: один прогрев после всех hex-пар

`_warmHexPair` возвращает текстуру реального hex draw. После завершения всех пар

## Асинхронная компиляция без смены шейдеров High

`tools/three/parallelCompile.js` переносит механизм lazy program initialization
из Three r158 на установленный r155. Официальные исходники для сверки:
[WebGLProgram r158](https://github.com/mrdoob/three.js/blob/r158/src/renderers/webgl/WebGLProgram.js)
и [WebGLRenderer r158](https://github.com/mrdoob/three.js/blob/r158/src/renderers/WebGLRenderer.js).
Это локальный backport жизненного цикла, а не обновление всего движка до r158.

- Vite получает один точный alias `three` для dev/prebundling и production.
  Генерируемый модуль находится в `node_modules/.cache/digital-monster`; npm-пакет
  не редактируется. В имени кеша — хеш результата. Исходный `three.module.js`
  проверяется по SHA-256: обновление зависимости требует явного пересмотра patch,
  иначе сборка останавливается. Сгенерированные файлы не коммитить и не править.
- `compileSceneChunked` отправляет задания с прежним CPU-бюджетом, не ожидая
  завершения каждого материала перед отправкой следующего. Перед выходом из
  helper он ждёт все отправленные программы. RT/cube face/mip возвращаются сразу
  после отправки, а исходные meshes/materials не переподчиняются.
- `compile()` собирает именно программы, включая обе стороны transparent
  DoubleSide. `compileAsync()` опрашивает неблокирующий `COMPLETION_STATUS_KHR`.
  Только после завершения читает LINK_STATUS, диагностику, uniforms/attributes.
  Сама работа компилятора остаётся, но ожидание отдельных программ перестаёт
  последовательно блокировать основной JS-поток.
- Невалидная программа отклоняет prepare. Ошибки pending Promises сразу имеют
  обработчик; потеря контекста/dispose прекращают опрос. Без
  `KHR_parallel_shader_compile` проверка остаётся синхронной внутри бюджетируемого
  задания — полный warm gate сохраняется, ускорение этого механизма недоступно.
- Реальные scene/hex/bloom/screen draw остаются под загрузчиком. После Start нет
  отложенной очереди компиляции. Обработка uniforms при обычном рендере сохранена;
  меняется момент первоначального получения locations, а не значения uniform.

### CPU: подписи правой дуги и чтение layout (2026-09-10)

### Проба локального света — `medium-local-v5`, требует доработки (2026-09-11)

Одна только круглая alpha-маска не исправила результат предыдущей пробы:
суммирование HDR-яркости и bloom продолжали создавать крупные квадратные
блики. В текущем Medium у кита используется bounded SCREEN accumulation:
`light + background * (1 - light)`. RGB света предварительно умножается на
alpha **после** fog; отдельные blend-факторы alpha сохраняют покрытие. Цвет
каждой частицы ограничен диапазоном 0..1, и наложение частиц друг на друга
больше не добавляет неограниченную HDR-энергию. Дополнительных RT, meshes,
GPU-проходов и Canvas uploads для этого не требуется.

Круглый центр и его локальный ореол вычисляются в одном fragment shader.
Под ореол выделен спрайт 9 физических пикселей при pointScale=6
(`uRasterScale=1.5`); видимый плотный центр меньше. Края затухают до границы
круга, углы отбрасываются. Вместо шести grain-сэмплов и экспоненциального
профиля используются smoothstep и полином. Пульсация, цветовой tint,
зональные fade, исходная геометрия и GPU skinning сохранены. High использует
свою прежнюю additive/grain-ветку.
