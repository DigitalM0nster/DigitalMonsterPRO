# Глитч-змейка текста: утверждённый GPU-способ

Пользователь одобрил этот эффект 9 сентября 2026 года на HUD «Связь с ядром» в `/capabilities/synthetic-core` и попросил сохранить его для повторного использования. Это визуальный и технический референс для будущих глитч-змеек текста. Сохранять характер движения, резкость букв, интервалы и подготовку ресурсов до взаимодействия.

## Как выглядит утверждённый эффект

Голова змейки проходит **по буквам**, временно заменяя их голубыми цифровыми символами. За головой остаётся чистый неподвижный текст. Первая строка раскрывается слева направо, вторая — справа налево, третья — снова слева направо. У головы есть короткий сдвиг горизонтальных полос; весь текст не дрожит. После завершения замены и сдвиги прекращаются.

При уходе курсора та же последовательность проигрывается обратно. Быстрое повторное наведение продолжает движение с текущей позиции, без сброса и вспышки полного текста. Статические заголовки можно исключить из змейки, как сделано в исходном HUD.

Не заменять этот эффект обычным fade-in, общей шторкой слева направо или непрерывным случайным перемешиванием всех букв. Не добавлять цветные RGB-контуры: утверждённая палитра — голубой/циан с переходом в исходный цвет текста.

## Рабочий исходник

Общие примитивы сферы и подписей крана теперь находятся в `src/three/objects/sceneHud`: `sceneHudAtlas.js` готовит атласы по данным сцены, `sceneHudShaders.js` содержит исходный рисунок колец, глитч-змейку и её обратимый playhead. Файлы Synthetic Core ниже сохраняют его тексты, состояния и композицию; второй потребитель — `Mmk1HotspotLabels.js`.

- [syntheticCoreHudAtlas.js](./scenes/capabilities/placeholders/syntheticCoreHudAtlas.js) — `createHudAtlas`: подготовка надписей, карты порядка букв и маленькой полосы символов.
- [syntheticCoreHudMaterials.js](./scenes/capabilities/placeholders/syntheticCoreHudMaterials.js) — `snakeLabel`, `assemblyLabel`, `activeLabel`: замены, фазы букв, чистый текст и дешёвые ветки для покоя. `PANEL_VERTEX` и `LINK_VERTEX` ограничивают растеризацию реальной областью элемента.
- [SyntheticCoreHud.js](./scenes/capabilities/placeholders/SyntheticCoreHud.js) — один обратимый `uSnake`, кешированный размер renderer, `setComposeMode`, `renderScreenOverlay`, освобождение ресурсов.
- [DigitalMonsterThreeApp.js](./app/DigitalMonsterThreeApp.js) — переключение этого HUD между screen и models до отрисовки кадра; вывод после bloom в покое.

Эти файлы являются исполняемым образцом. Способ переносимый; конкретные подписи, размеры, число строк, состояния ядра и привязка к сфере принадлежат этой сцене, их не следует копировать в другой интерфейс автоматически.

## Три подготовленных ресурса

### 1. Атлас чистого текста

После загрузки шрифта один раз нарисовать все нужные состояния и локали через Canvas2D. Сохранить CanvasTexture и использовать её при каждом наведении.

В исходнике одна ячейка занимает 300 × 200 CSS-пикселей. Три локали размещены по горизонтали, шесть состояний — по вертикали. Полный canvas: `900 × 1200 × rendererPixelRatio` по соответствующим измерениям; DPR в образце ограничен диапазоном 1–2.

Буквы рисуются отдельно, с явным продвижением позиции, без сжатия строки через `fillText(..., maxWidth)`. Утверждённые интервалы: 1,4 px для размеров от 14 px, 1,1 px для меньших; пробел — `fontSize * 0.55`. Мелкий текст — 10 px, заголовок — 12 px, число модулей — 16 px. Сохранять читаемые интервалы при адаптации.

### 2. Компактная карта порядка букв

Во время подготовки текста сохранить метрики каждой буквы: начало X, ширину, размер шрифта и строку. Собрать последовательность с разворотом каждой второй строки; пробелы пропустить, сохранив их визуальную ширину.

Карта — `DataTexture` RGBA8. Для каждой строки текста нужна **одна строка данных**, а не картинка высотой во весь текст. В исходнике: 900 × 18 × 4 = **64 800 байт**, независимо от DPR.

Каждый X-пиксель внутри диапазона буквы содержит:

| Канал | Значение |
| --- | --- |
| R | Порядок буквы: `(index + 0.5) / glyphCount`, закодированный в 0–255 |
| G | Локальная координата X внутри буквы, 0–255 |
| B | Размер шрифта в CSS-пикселях |
| A | 255 для диапазона буквы, 0 для пустого места |

Фильтрация карты — nearest, без цветового преобразования и mipmaps. Не интерполировать метаданные соседних букв. Учитывать ориентацию UV: карта данных и CanvasTexture используют разные соглашения о перевороте Y.

Размеры карты, индексы строк, границы строк и baseline в шейдере должны соответствовать фактическому layout. Для существенно более длинного текста делить эффект на секции или повышать точность порядка: 8-битный R имеет 256 уровней и не подходит для произвольно длинной последовательности без потери точности.

### 3. Маленький атлас символов-замен

Один раз нарисовать полосу `0123456789ABCDEF<>/+=*#?[]` тем же шрифтом. В образце ячейка — 20 × 32 CSS-px, растрирование в 2×. Во время эффекта GPU выбирает готовый символ и помещает его в диапазон текущей буквы.

Не создавать полноразмерные копии всех текстовых состояний для каждого кадра глитча. Полоса символов и компактные метаданные намного меньше таких копий.

## Один playhead и фаза буквы

В общем update сцены менять только числа/uniforms. Использовать `delta` в секундах из владельца render loop; в исходной сцене он ограничен 0–0,05 s.

```js
uSnake.value = clamp(
  uSnake.value + delta * (detailsRequested ? 1 / 1.15 : -1 / 0.48),
  0,
  1,
);
```

Появление занимает 1,15 s, уход — 0,48 s. Не присваивать `0` при каждом pointerenter: один playhead делает смену направления непрерывной. Плавность фона панели управляется отдельно (`uDetails`); она не должна превращать змейку букв в общий fade.

Для каждой буквы шейдер читает `order` из карты:

```glsl
float phase = clamp((uSnake - (0.01 + order * 0.80)) / 0.19, 0.0, 1.0);
float head = smoothstep(0.02, 0.10, phase)
           * (1.0 - smoothstep(0.76, 0.96, phase));
float settled = smoothstep(0.78, 1.0, phase);
float frame = floor(clamp((phase - 0.08) / 0.72, 0.0, 0.999) * 3.0);
```

Детерминированный hash от порядка буквы, состояния и `frame` выбирает один из символов. Всего три смены символа за фазу буквы. Семь горизонтальных полос дают небольшой сдвиг X только у головы: амплитуда `0.16 * head` в локальных UV буквы. Это не непрерывный шум по времени на всей строке.

Финальная альфа — максимум маски символа-замены и маски чистой буквы с `settled`. Цвет переходит от циана к исходному цвету по доле чистой буквы. Координаты символа ограничиваются его ячейкой, чтобы не захватывать соседний символ.

## Общий звук букв

Все змейки используют утверждённый звук сферы: профиль `src/sounds/letterSnakeSound.js` задаёт запись `about_particles`, громкость, скорость и lowpass-фильтр. GPU-подписи передают фактически нарисованный playhead в `CapabilitySceneSound`; DOM и эффекты с известной длительностью вызывают `playGlitchTextSound`. Не выбирать отдельную запись или тихий профиль для новой сцены.

Звук следует появлению и обратному уходу букв, затухает у конца и молчит при неподвижном тексте. Одновременные строки делят один голос. Запись декодируется общим кешем под прелоадером; наведение не запускает загрузку нового ресурса. Сохранять общий mute, остановку скрытой/неактивной сцены и существующее панорамирование меню.

## Обязательные ограничения производительности

- Загрузить шрифт, построить атласы, геометрию и материалы до Start. Включить их в существующую подготовку и настоящий RT draw под прелоадером. Одной компиляции недостаточно.
- После Start при обычных наведениях не вызывать `fillText`, `measureText`, `texture.needsUpdate`, создание/удаление textures, meshes, materials или programs. Все варианты интерактива уже подготовлены.
- Не обходить буквы на CPU каждый кадр. Не создавать отдельный DOM-элемент, mesh, timer или tween для каждой буквы. Порядок вычисляется один раз; анимация управляется одним числом.
- Не запускать отдельный бесконечный rAF для эффекта. Использовать update владельца сцены, прекращать работу неактивной сцены.
- Размер брать из кеша renderer (`renderer.getSize` в подготовленный Vector2). Не читать `clientWidth`, `clientHeight` или `getBoundingClientRect` в каждом update/draw ради layout этого HUD.
- Растеризовать прямоугольник самого элемента. В исходнике панель — 300 × 200 CSS-px, линия связи — её ограничивающий прямоугольник с небольшим запасом. Full-screen quad с последующим discard всё равно запускает лишние фрагменты.
- При `uSnake <= 0` детальный текст сразу прозрачный. При `uSnake >= 1` читать только чистую надпись, без order map, символов или glitch-расчётов. При стабильном выбранном состоянии не семплировать все скрытые варианты.
- Не добавлять fullscreen blur, feedback render targets, RGB-смещение или отдельный bloom ради змейки.
- При настоящем изменении контента подготовить нужные ресурсы отдельно от анимации. Событие наведения не должно становиться скрытым этапом загрузки.
- На dispose освобождать все три текстуры и оставлять владельцу сцены корректную возможность освободить геометрию/материал, в том числе если панель временно находится в overlayScene.

## Резкость и переходы

### Несколько состояний: один вызов змейки в цикле

`syntheticCoreHudMaterials.js` смешивает шесть состояний: обычное, наведение на
сферу и ответ на импульс, каждое в собранном/раскрытом виде. С 10.09.2026
`activeLabel` использует веса состояний и один вызов `snakeLabel` внутри цикла.
Не возвращать вложенную цепочку `activeLabel → assemblyLabel → snakeLabel`:
на контрольной машине она давала две синхронные компиляции по ~1,4 с.

Математика прежняя: `mix(A, B, t) = A * (1-t) + B * t`. Для наведения `H`,
импульса `P` и раскрытия `O` веса групп равны
`[(1-P)*(1-H), (1-P)*H, P]`. Каждая группа делится между собранным состоянием
с множителем `1-O` и раскрытым с множителем `O`. Сумма шести весов равна 1.
Сохраняются исходные быстрые ветки `<0.001` / `>0.999`; нельзя вводить новый
порог отсечения малых произведений весов, иначе изменятся промежуточные кадры.

Каждый индекс 0…5 встречается в цикле один раз, нулевой вес пропускается.
Смешиваются исходные RGBA-результаты; менять это на несколько отдельных
alpha-blended draw нельзя без проверки эквивалентности прозрачности.
Статический заголовок и дешёвые ветки скрытой/завершённой змейки сохраняются.

Это упрощение структуры компиляции, а не кеширование пикселей между кадрами.
Старая версия тоже часто вычисляла каждое активное состояние только один раз
за пиксель благодаря взаимоисключающим веткам. Не приписывать изменению
многократное ускорение runtime GPU без отдельного измерения.

Контроль: 231 сочетание трёх языков, фаз змейки, состояний и значений около
порогов; при сравнении реальных 600×400 RGBA8 RT старого и нового шейдеров
разница пикселей — 0. Полный cold-start A/B: две компиляции HUD
1452/1389 → 85/87 мс. Полная подготовка 16,32 → 13,64 с. GPU draw смешанного
состояния: около 0,021 → 0,019 мс (12 GPU timer-query замеров варианта).
Это измерения на Chrome / RTX 3070 Ti, не универсальные бюджеты.

### Композиция текста

Текст в покое выводится **после bloom**, на финальный canvas, в размере renderer DPR. Используются nearest-фильтрация, отсутствие mipmaps и привязка позиции к пикселям renderer. Не возвращать размывающую тень Canvas2D и не применять альфу букв дважды: повторное умножение ослабляет тонкие штрихи.

Во время hex-перехода тот же подготовленный mesh переносится в models-слой и участвует в переходе вместе со сценой. Одновременно не рисовать его screen-overlay. После отмены/завершения перехода восстановить правильный режим до отрисовки кадра. Не пересоздавать ресурсы при переносе между слоями.

Соблюдать [SITE_TRANSITION.md](./render/transition/SITE_TRANSITION.md) и [PAGE_INTERACTION.md](./render/transition/PAGE_INTERACTION.md): hover и click принимает только владелец текущей экранной Y-полосы; глобальное меню сохраняет собственные правила.

## Проверка при повторном использовании

1. Посмотреть начало, середину и конец появления. Видны последовательные замены букв и поворот змейки между строками; в конце текст полностью чёткий, без остаточного шума и обрезанных символов.
2. Быстро уйти/вернуться несколько раз, проверить touch, resize и поддерживаемые локали. Playhead продолжает текущую фазу; интервалы и переносы не ломаются.
3. После Start проверить первый и повторные hover: версии трёх текстур и UUID геометрии/материалов не меняются; нет вызовов рисования текста и загрузок текстур из этого эффекта.
4. Проверить GPU-программы и console на ошибки. Измерять отдельно время update HUD и итоговый кадр; низкая стоимость JavaScript не доказывает низкую стоимость GPU.
5. Проверить начало/отмену hex-перехода и уход/возврат на страницу. Нет двойного рисования, вспышек, восстановления размытых букв или работы скрытой сцены.

В проверке исходной реализации: 0 перерисовок текста, 0 вызовов `texImage2D`/`texSubImage2D` в измеренном окне взаимодействия, стабильные ресурсы; P95 update HUD около 0,1 ms на 70 измеренных кадрах в headless Edge, 1440 × 900, low tier. Это результат конкретного прогона, **не гарантия времени кадра на любом устройстве**. При переносе заново проверить стоимость и реальные ограничения новой сцены.
