# WebGPU: пакет заданий для GPT-5.3-Codex-Spark

Подготовлен 2026-09-14. Статус: подготовка завершена; миграция и измерения не начаты.
Начинать реализацию после завершения основной версии сайта и команды пользователя.

Цель первого цикла: перенести одну настоящую сцену и переход с hex/bloom,
сравнить WebGPU с WebGL при одинаковой картинке и решить, оправдан ли полный перенос.
Рост FPS не предрешён. Пакет уменьшает объём повторного исследования, но не гарантирует
равенства возможностей Spark и Astra. Никакие показатели ускорения пока не измерены.

## Как пользоваться

Первый запуск: отправить стартовый промпт ниже. Затем отправлять промпт продолжения.
Один запуск выполняет один небольшой завершённый шаг. Большие этапы делить на шаги
с явно названными входами, файлами и проверкой. Не передавать модели весь старый чат.
Состояние между запусками хранить в разделе «Контрольная точка» в конце этого файла.

### Стартовый промпт

```text
Основная версия Digital Monster завершена. Начинаем подготовленный WebGPU-прототип.
Прочитай AGENTS.md и src/three/WEBGPU_SPARK_HANDOFF.md.
Соблюдай раздел «Рабочий контракт». Выполни только этап 0.
Сверь устаревающие сведения с текущими файлами. Не начинай миграцию или обновление
зависимостей в этом запуске. Сохрани результат и следующий точный шаг в контрольной
точке этого файла. Итог: до 8 строк с результатом, проверкой и следующим шагом.
```

### Промпт продолжения

```text
Продолжи WebGPU-прототип по src/three/WEBGPU_SPARK_HANDOFF.md.
Прочитай рабочий контракт, контрольную точку и только следующий нужный этап.
Выполни следующий небольшой шаг, сохраняя ограничения AGENTS.md.
Не повторяй завершённый аудит и успешные проверки без новых изменений.
После достаточной проверки обнови контрольную точку: что сделано, доказательства,
что не проверено и следующий точный шаг. Не переходи к следующему этапу в этом запуске.
```

## Рабочий контракт

- Источник обязательных правил — [AGENTS.md](../../AGENTS.md). Этот файл — задание,
  не замена правил. Свежий код и документация выбранной версии важнее снимка ниже.
- Только `C:/websites/develope/DigitalMonsterPRO`, ветка `main`. Перед записью проверить
  cwd, `git branch --show-current` и `git status --short`. Без веток, worktree, detached
  HEAD, reset, stash чужой работы и параллельных записей. Чужие изменения сохранять.
  Если нужный файл прямо сейчас изменяется другой задачей — сначала согласовать запись.
- Не запускать другие модели или агентов. Коммиты, push и публикацию не выполнять
  без соответствующего запроса. Подготовка прототипа не означает публикацию.
- Читать только владельца изменяемой подсистемы, ближайшие зависимости и нужный раздел
  обязательной документации. Независимые поиски объединять; вывод ограничивать.
- Перед правкой кратко назвать результат и целевые файлы. При росте шага свыше шести
  файлов сообщить об этом и выделить меньший законченный шаг. Не скрывать необходимую
  сложность и не жертвовать корректностью ради лимита файлов.
- Сохранять текущий WebGL-путь как рабочий эталон. Эксперимент сначала доступен только
  через явно включаемый режим. Не загружать оба движка без необходимости.
- Один активный renderer/canvas/render loop и один владелец сцен/прогресса.
  Альтернативный графический backend не должен становиться вторым параллельным runtime.
- Не менять дизайн, плотность частиц, DPR, материалы или эффекты ради красивых цифр.
  Оптимизацию алгоритма и снижение качества обозначать раздельно.
- До реализации неизвестного WebGPU/TSL API проверить официальную документацию
  конкретной выбранной версии. Сохранить ссылку и решение; не выдумывать методы.
- Если проверка недоступна, написать «не проверено», причину и точный способ проверки.
  Компиляция, успешная сборка и отсутствие ошибок не доказывают визуальное равенство.
- Одинаковую неуспешную попытку повторять не более одного раза без новой информации.
  После двух разных исправлений одной проблемы без результата сохранить симптомы,
  гипотезу, команды и минимальный воспроизводимый случай; не расширять переписывание.

## Инварианты реализации

1. Все нужные интерактивные ресурсы подготовлены до Start: загрузка, декодирование,
   построение, компиляция и реальные GPU draws. Работа разбита между кадрами;
   `compile()` не заменяет draw. Готовность ожидает асинхронную подготовку backend.
2. Обычные переходы после Start не создают и не уничтожают основные меши, материалы,
   текстуры или GPU-программы. Dormant — сохранённый ресурс, а не teardown.
3. Prepared text/HUD анимируется uniforms, масками и transforms. Не рисовать целую
   панель в Canvas2D каждый кадр и не загружать её заново на GPU ради анимации.
4. HUD в покое резкий, после bloom; в hex запекается в нужный слой без двойного вывода.
   About и case enter имеют разные правила — не объединять их поведение механически.
   HTML-дуга и project-nav сохраняют свой текущий путь.
5. Единственный progress owner, обратимость и отмена перехода, next-only dormant,
   Y-band принадлежность кликов. Global chrome остаётся доступным.
6. Device/context loss, unmount и повторная инициализация не оставляют утечек,
   дублирующих listeners или loops. Переключение backend требует подготовки перед
   показом картинки; нельзя холодно менять renderer посреди анимации.
7. Автоматический WebGL2-backend нового WebGPURenderer не равен сохранённому старому
   WebGLRenderer. Compute-возможности WebGPU не имеют универсального WebGL-fallback:
   для них нужен совместимый алгоритм. Сохранять разницу явной в коде и отчёте.

## Этап 1 — измеримый WebGL-эталон

Задание для Spark: зафиксировать baseline до изменения рендера. Переиспользовать
существующую диагностику; при необходимости добавить маленькую dev-only проверку
реальных финальных отрисовок. Несколько RT-проходов одного кадра считать одним кадром.
CPU-время отправки команд не называть GPU-временем; GPU timers использовать только
при поддержке и без синхронного ожидания GPU каждый кадр.

Зафиксировать commit и относящийся к эксперименту diff, браузер, устройство/GPU,
ОС, частоту экрана, viewport, DPR сцены/UI, качество, питание, доступные эффекты.
При сравнении A/B закрепить те же настройки; автоадаптацию измерять отдельно.
Сохранить изображения одинаковых состояний: покой, середина hex, отмена, возврат.
Покрыть первую навигацию после Start, прогретую навигацию и несколько минут работы.

Метрики: реальные финальные render submissions, rAF отдельно, интервалы кадров
p50/p95/p99, длинные кадры, CPU/GPU время при доступности, загрузка/прогрев/память.
Render submissions не доказывают число кадров, фактически показанных экраном;
использовать браузерные frame traces при доступности, иначе обозначить ограничение.
Для основных одинаковых сценариев выполнить 3 коротких прогона по 10–20 секунд,
чередуя backend в будущем A/B. Не путать лимит дисплея с запасом производительности.

Готово: есть исходные результаты и воспроизводимые действия. Не подменять недоступное
устройство эмуляцией viewport. Отсутствующие физические устройства отметить.

## Этап 2 — запуск экспериментального backend

Задание для Spark: по решению этапа 0 подключить выбранную версию и минимальный
экспериментальный режим через существующую точку владения renderer.
Текущий режим остаётся доступным. Проверять успешные adapter/device/init,
а не только наличие `navigator.gpu`. Ошибка запуска должна приводить к рабочему
WebGL-пути с корректным cleanup; исключить бесконечный цикл повторных запусков.

Перенести по одному материалу/узлу сцены в маленьких шагах. До готовности всех нужных
частей не выдавать частично перенесённую сцену за завершённый эксперимент.
Не обходить проблемы отключением HUD, bloom, цвета или существующих эффектов.

Готово: обе сцены прототипа работают в экспериментальном режиме; сохранён текущий
режим; проверены включение, отсутствие поддержки и отказ инициализации, resize,
cleanup. Изменение зависимостей требует build и соответствующих проверок.

## Этап 3 — hex, bloom и композиция

Задание для Spark: переносить по одной подсистеме в порядке hex → bloom → финальная
композиция. Использовать действующие источники progress/camera, не писать второй
контроллер навигации. Сохранять форматы/цветовое пространство/alpha/порядок слоёв.
TSL/API сверять с выбранной версией. Объединять проходы только при сохранении результата.

Готово: прямой/обратный переход выбранной пары, медленный/быстрый scroll, большой delta,
touch и немедленная смена направления работают. Отмена возвращает валидную сцену;
клики в частично открытых страницах подчиняются Y-bands. Не удалён эффект ради скорости.

## Проверки и формат передачи результата

Документация: diff. Локальный JS/JSX: lint изменённых файлов. Логика: ближайший
осмысленный тест. Конфиги/зависимости/сквозная интеграция: build и необходимые
расширенные проверки. Команды определить по текущему проекту: сейчас есть `dev`,
`build`, `lint`, `preview`; готового `npm test` нет. Не устанавливать новый test stack
ради пакета. Требования визуальных/runtime-проверок AGENTS.md этим не сокращаются.

Для неизменившихся результатов сохранять доказательства вместо повторного прогона.
При новом изменении перепроверять затронутые сценарии; финальная интеграция требует
проверки системы целиком. Недоступную обязательную проверку не отмечать выполненной.

Если модель застряла, передать до 15 строк: цель шага, файлы, точный симптом,
воспроизведение, уже проверенные гипотезы, фрагмент ошибки, один нерешённый вопрос.
Пользователь сможет адресовать этот вопрос более сильной модели без всего старого чата.

- При продолжении дописывать: этап/шаг; commit + относящийся diff; изменённые файлы;
  выбранные версии и backend; проверки с результатами и путями к доказательствам;
  оставшиеся проблемы; следующий шаг с точными входами и критерием завершения.
